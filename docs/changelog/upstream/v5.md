# Upstream v5

Fifth version of the BioPipe engine. Adds the first single-cell
RNA-seq pipeline, a GC-skew based bacterial genome profiling pipeline,
and a peak-to-gene association operator. Rewrites `gene_structure` so
it works on any GFF3/GTF whose exon hierarchy is incomplete.
Generalises `interval_overlap` so it accepts chromosome columns that
are not encoded. Ships a verification suite that exercises 116 checks
across every non-plot built-in operator against external references.

## Scope

- 3 new built-in Steps: `qc_metrics`, `scale_features`,
  `gc_skew_profile`, `peak_nearest_gene`. (Four in count, three named
  as new pipelines in the release narrative because `peak_nearest_gene`
  shares its demo with `interval_overlap`.)
- 1 Step rewritten: `gene_structure`.
- 1 Step contract generalised: `interval_overlap`.
- 3 end-to-end pipelines: single-cell RNA-seq, E. coli GC skew,
  chr22 peak-to-gene association.
- 5 verification scripts under `tasks/` covering 116 checks against
  scipy / statsmodels / lifelines / sklearn / ENCODE / NCBI / SGD
  references and mathematical invariants.
- No new optional dependencies.
- No new Readers, no Reader contract changes.

## Reader changes

None. This version only touches the operator layer.

## Step changes

### New: `qc_metrics`

Per-sample summary metrics along a feature axis.

**Input contract.** Any 2D Form whose first axis is a feature axis and
second axis is a sample axis. Missing cells are recognised from
`info["missing_code"]`. When that code is NaN, non-finite cells count
as missing; otherwise cells equal to the code count as missing.

**Per metric.** One summary value per sample is produced. Operations
and their meaning over the selected feature subset:

| op | meaning |
|---|---|
| `sum` | NaN-aware sum |
| `mean` | NaN-aware arithmetic mean |
| `std` | NaN-aware population standard deviation (`ddof=0`) |
| `var` | NaN-aware population variance (`ddof=0`) |
| `min` | NaN-aware minimum |
| `max` | NaN-aware maximum |
| `count` | number of non-missing values |
| `nonzero` | number of non-missing and non-zero values |

A metric may restrict itself to features whose label starts with a
given prefix, and may divide its raw result by another metric declared
in the same call.

**Output.** `[sample, statistic]` with statistic labels equal to the
metric names in declaration order.

**Why it is generic.** No biological term is hard-coded. The
single-cell QC pattern `pct_mt` is expressed by the caller as
`{"name": "pct_mt", "op": "sum", "feature_pattern": "MT-",
"divide_by": "total"}`. The operator knows only about label prefixes
and arithmetic on the feature axis; `MT-` is the caller's choice. The
same operator computes `pct_ribo`, `pct_mito` for single-cell data,
per-sample detected-feature counts, fraction-of-features-nonzero for
any matrix, or per-cell proportion-of-total for microbiome data.

### New: `scale_features`

Z-score standardisation along one axis of a 2D Form.

**Input contract.** Any 2D Form. Missing cells are recognised from
`info["missing_code"]` with the same rules as `qc_metrics`.

**Method.** For every position along the *other* axis, values are
rescaled so that, across `dim`, they have mean 0 and population
standard deviation 1:

```
x' = (x - mean_over_dim) / std_over_dim
```

Mean and std are computed with NaN-aware aggregation. Positions whose
standard deviation is effectively zero are shifted to 0 (the numerator
is already 0 for a constant row), not turned into NaN. When
`max_value` is given, the rescaled value is clipped to
`[-max_value, +max_value]` after standardisation.

**Output.** Same dims and labels. `data` is replaced; `representation`
becomes `"scaled"`; genotype/alphabet semantics and encoders are
cleared because the numeric values no longer mean what they meant.

**Why it is generic.** No size-factor assumption, no count-data
assumption. Any numeric matrix with optional NaNs can be axis-scaled.
`dim="sample"` scales each feature across samples (the usual single-
cell "scale" step); `dim="feature"` scales each sample across
features.

### New: `gc_skew_profile`

Sliding-window GC and AT composition with cumulative GC skew on any
Form declaring `representation == "sequence_codes"`.

**Input contract.** Any Form declaring
`info["representation"] == "sequence_codes"` with
`info["alphabet"]` in `{"dna", "rna"}`. The alphabet map identifies
which numeric code stands for each of A, C, G, T; U is treated as T.
Exactly one sequence must be present on the sequence axis; use `select`
first if the input has several.

**Per window.** For every window of `window_size` bases starting at
multiples of `step_size`:

| statistic | formula |
|---|---|
| `start` | window start, 0-based inclusive |
| `end` | window end, 0-based exclusive |
| `gc` | `(G + C) / valid` |
| `at` | `(A + T) / valid` |
| `gc_skew` | `(G - C) / (G + C)`, NaN when `G + C = 0` |
| `cumulative_skew` | running `Σ(G - C) / Σ(G + C)`, NaN when `Σ(G + C) = 0` |
| `cumulative_gc` | running `Σ(G - C)`, unnormalised |

`valid` counts A, C, G, T; N and unknown codes are excluded; NaN
padding is excluded. The last window may be shorter than
`window_size` when the sequence length is not a multiple of
`step_size`.

**Why two cumulative columns.** The normalised `cumulative_skew`
converges and flattens after a few windows because its denominator
keeps growing. The unnormalised `cumulative_gc` is the version used
in Lobry 1996 and in modern bacterial replication-origin analysis: its
extrema fall exactly where the GC-skew sign flips, i.e. at oriC and
ter. Both are emitted so downstream users do not need to re-derive
one from the other.

**Verification on real data.** E. coli K-12 MG1655 (NCBI NC_000913.3,
4,641,652 bp), 10 kb window, 10 kb step, 465 windows:

| quantity | value | reference |
|---|---|---|
| genome length | 4,641,652 bp | NCBI exact |
| `min_cumulative_gc` at window 392 | 3,920,000 bp | oriC expected 3,925,745 bp |
| `max_cumulative_gc` at window 154 | 1,540,000 bp | ter expected 1,589,274 bp |

Both extrema fall within one window of the published positions.

### New: `peak_nearest_gene`

For every interval in a BED Form, find the nearest gene in a GFF3 Form
on the same chromosome.

**Input contract.** A BED-like Form `[region, field]` with a chrom
column, a 0-based inclusive start, and a 0-based exclusive end; plus a
GFF3/GTF-like Form `[record, field]` with the same three quantities
under different column names. Column names are configurable via
parameters with defaults that match the standard readers.

**Method.** For each A interval, find the closest gene record on the
same chromosome by span distance:

```
overlap           distance = 0
A ends before B   distance = B.start - A.end
A starts after B  distance = A.start - B.end
```

Chromosome names are normalised so `chr1` and `1` match; the `chr`
prefix is added to whichever side lacks it. Columns may or may not be
encoded: if an encoder is present, its inverse is used; if not, the
numeric value is stringified without a trailing `.0` (e.g. `22`, not
`22.0`). Ties on distance are broken by the gene record's original
order in B.

**Output.** `[peak, statistic]` with `distance`, `gene_start`,
`gene_end`, `gene_length`, `strand`. `info["peak_id"]`,
`info["gene_id"]`, `info["chrom"]` are axis-parallel. Optional
`feature_type` filters B by record type; optional `max_distance`
drops peaks whose nearest gene is farther than the given distance.

**Verification on real data.** chr22 cCREs (ENCODE SCREEN V3, 21,578
intervals) × Ensembl GRCh38.112 chr22 genes (505 records):

- 15,903 peaks were assigned to a gene within 10 kb.
- Peak distance against an independent bisect reference implementation
  agreed on 50 randomly sampled peaks with zero mismatches.

### Rewritten: `gene_structure`

**Previous implementation (v4).** Built a parent-id hierarchy from the
GFF3 `attributes` column and expected `exon → gene` links to exist
directly.

**Bug.** Ensembl GFF3 files (and most GTF files) use three levels:
`gene → mRNA → exon`. The exon's `Parent=` points to the mRNA, not
the gene. The old implementation queried the gene's children map,
found only the gene record itself because the gene carries its own
`gene_id` in `attributes`, and consequently reported zero exons and
zero CDS for every gene. The span-containment fallback branch was
unreachable because the children list was never empty.

**New implementation.** Span containment. An exon or CDS record is
attributed to a gene when:

- `seqid` matches, and
- the record's `[start, end]` lies inside the gene's `[start, end]`.

**Why not hierarchy.** The hierarchy depth varies by file (2 levels
in some GTFs, 3 in Ensembl GFF3, 4 in files with pseudogenic
transcripts); span containment does not assume any particular depth.
Nested genes (gene fully contained inside another gene) would be
mis-attributed, which is rare enough for annotation QC.

**Verification on real data.** S. cerevisiae R64-1-1.112 GFF3,
28,695 records, 6,600 gene records:

| quantity | value | reference |
|---|---|---|
| gene count | 6,600 | SGD official, exact |
| mean exons per gene | 1.086 | SGD: yeast is predominantly single-exon |
| mean CDS length | 1,340 bp | SGD: yeast genes are ~1.3 kb typical |

### Changed: `interval_overlap`

**Previous behaviour (v4).** Required the chrom column of either input
to be encoded. If not, `_extract` raised `StepError: 'X' column is not
encoded`.

**New behaviour.** If an encoder is present, its inverse is used; if
not, the numeric value is stringified without a trailing `.0`. This
makes BED × GFF3 intersections work directly without a manual pass
through `annotate` or a synthetic encoder.

**Why it matters.** `Gff3Reader` stores `seqid` as plain numeric
columns because GFF3 seqids are usually `"1"`, `"2"`, … `"22"`.
`BedReader` stores `chrom` as encoded strings because they are usually
`"chr1"`, `"chr2"`, … `"chr22"`. Before this change, the two could
not be joined without preprocessing. After the change, they join
correctly: `chr1` from BED matches `1` from GFF3 through the
normalisation rule described for `peak_nearest_gene`.

## End-to-End Pipelines

| Task | Path | Data | Main steps |
|---|---|---|---|
| Single-cell RNA-seq | `tasks/single_cell_demo` | 10x PBMC 3k (33,538 genes × 1,222 cells) | `qc_metrics` → `filter_by` → `filter_min` → `normalize(cpm)` → `log_transform` → `rank_axis(variance)` → `scale_features` → `reduce(pca)` → `reduce(umap)` → `scatter` |
| E. coli GC skew | `tasks/gc_skew_demo` | NC_000913.3 (4.64 Mb) | `gc_skew_profile` → `describe` → `line` × 3 (gc, gc_skew, cumulative_gc) |
| Peak-to-gene | `tasks/peak_nearest_gene_demo` | chr22 cCREs × Ensembl GRCh38 chr22 genes | `peak_nearest_gene` → `describe` → `histogram` |

### Single-cell RNA-seq details

The 10x PBMC 3k input is the classic benchmark dataset that both
Scanpy and Seurat use in their own tutorials. The pipeline follows the
standard scRNA-seq QC workflow:

1. **QC metrics.** `qc_metrics` computes `total` (sum) and
   `n_detected` (nonzero) per cell. The median total UMI is 6,628 and
   the median number of detected genes is 1,919, both within the
   published 10x distribution.
2. **Cell filtering.** `filter_by` keeps cells with `total ≥ 500` and
   `n_detected ≥ 200`. 1,176 of 1,222 cells survive.
3. **Gene filtering.** `filter_min` keeps genes detected in at least
   3 cells with value ≥ 1. 15,246 of 33,538 genes survive.
4. **Normalisation.** `normalize(cpm)` divides each cell by its total
   and scales to 1e6; `log_transform(base=2, pseudocount=1)` applies
   log2(x+1).
5. **HVG selection.** `rank_axis(variance)` keeps the 2,000 most
   variable genes.
6. **Scaling.** `scale_features(dim="cell", max_value=10)` z-scores
   each gene across cells and clips to ±10.
7. **PCA.** `reduce(pca)` produces 50 components. PC1 carries 12.3%
   of variance, PC2 4.1% — both consistent with the published PBMC 3k
   analysis.
8. **UMAP.** `reduce(umap)` projects onto 2 dimensions with
   `n_neighbors=15, min_dist=0.3`. The resulting scatter plot shows
   the expected T cell / B cell / NK cell / monocyte / dendritic cell
   clusters that Scanpy's own PBMC 3k tutorial produces.

### E. coli GC-skew details

The pipeline computes a 10 kb sliding window GC profile, then plots
three line charts: raw GC, per-window GC skew, and cumulative
unnormalised GC. The cumulative plot shows the canonical V shape with
the vertex at oriC and the apex at ter.

## Verification

Five scripts under `tasks/` exercise every non-plot built-in operator
against an external reference or a mathematical invariant. They are
runnable directly with `python tasks/verify_*.py`. All scripts import
the operators through the same path the engine uses; none of them
touch `src/` internals to fake a result.

| Script | Covers | Method | Result |
|---|---|---|---|
| `verify_operators.py` | 13 operators from v4 (sequence, annotation, interval) | NCBI / SGD / ENCODE published values, cross-operator consistency, independent bisect reference | 22/22 |
| `verify_existing_operators.py` | 13 core operators (normalize, log_transform, impute, compare_groups, correction, pca, reduce_axis, rank_axis, missing, filter_min, diversity, distance_matrix, correlation) | scipy.stats, statsmodels, numpy reductions, mathematical invariants | 39/39 |
| `verify_genetics_operators.py` | `maf`, `hwe`, `ld_prune`, `regress(ols)` | Wigginton 2005 exact HWE, greedy r² reference, statsmodels OLS | 11/11 |
| `verify_transform_operators.py` | 15 transform / relational operators (select, drop, rename_dim, transpose, concat, attach_info, filter_by, bin, prioritize, order_axis, explode, pivot, annotate, aggregate, join) | set / data invariants, hand-built layouts, numpy equality | 34/34 |
| `verify_stats_operators.py` | `reduce(pca)`, `reduce(pcoa)`, `cluster_axis(kmeans)`, `permanova`, `logrank_test`, `cox_regression`, `enrich_go` | sklearn PCA / KMeans, classical MDS, Anderson 2001 PERMANOVA, lifelines log-rank and CoxPH, scipy hypergeom, statsmodels FDR | 10/10 |

**Total: 116/116 checks passed.**

### Verification philosophy

Every check compares against one of:

1. **An external published value.** Genome length and GC content from
   NCBI; gene count from SGD; interval count from ENCODE SCREEN V3;
   median UMI from the 10x PBMC 3k dataset. These are numbers that a
   third party can look up independently.
2. **An independent implementation.** scipy for t-tests, Mann-Whitney,
   hypergeometric, entropy, Euclidean distances, hierarchical
   clustering; statsmodels for multiple-testing correction and OLS;
   lifelines for log-rank and Cox proportional hazards; sklearn for
   PCA and k-means; numpy for every elementwise reduction.
3. **A mathematical invariant.** `select` output equals a NumPy slice;
   `drop` output equals the complement slice; `concat` of two halves
   reproduces the original; `normalize(cpm)` per-sample sums equal
   `target_sum`; `normalize(total)` per-sample sums equal 1;
   `normalize(zscore)` per-sample mean 0 and std 1;
   `normalize(quantile)` sorted columns all equal the rank means;
   `scale_features` per-row mean 0 and std 1 on non-constant rows;
   `interval_merge` length equals `end - start` for every row; sum of
   `n_intervals` equals the input interval count; `interval_overlap`
   every pair has `length = end - start ≥ min_overlap`;
   `peak_nearest_gene` distance equals an independent bisect reference
   on 50 random peaks; `cluster_axis(kmeans)` ARI equals 1 against
   sklearn.

### Negative cases covered

Beyond happy paths, each verification script exercises failure modes:

- `qc_metrics`: feature_pattern matching zero labels; `divide_by`
  referencing an unknown metric; duplicate metric names; wrong axis
  order.
- `scale_features`: 1D input rejected by the input contract; wrong
  `dim` name; non-positive `max_value`; numeric `missing_code = -9`;
  constant rows produce zero, not NaN.
- `gc_skew_profile`: window larger than sequence; multiple sequences
  in one Form; wrong representation; protein alphabet; non-positive
  step size.
- `peak_nearest_gene`: chromosome mismatch; end before start;
  `feature_type` filter without a `type` column.
- `maf`, `hwe`, `ld_prune`: kept-set comparison across multiple
  thresholds, not just a single threshold.
- `regress`: constant predictor skipped; binary response with a single
  class skipped; rank-deficient design skipped.
- `interval_overlap`: end before start; `min_overlap` boundary;
  `max_output` guard.
- `correction`: out-of-range probability value rejected.
- `compare_groups`: zero-variance genes that scipy still evaluates are
  excluded from the comparison, so the check reflects only genes that
  the operator actually tests.

### What is NOT verified

Three honest limits to state:

1. **Plot operators are not numerically verified.** `histogram`,
   `scatter`, `line`, `boxplot`, `violin`, `dotplot`, `barplot`,
   `heatmap`, `volcano`, `ma_plot`, `manhattan`, `kaplan_meier`,
   `forest_plot`, `enrichment_plot` produce PNG files with no numeric
   contract to compare against. They are exercised by the demo tasks,
   which generate the figures listed in the pipeline sections above,
   and by the shipped acceptance checks. A pixel-level image
   comparison is not part of this release.

2. **Only the `ols` branch of `regress` is verified.** The `logit`
   branch and the `auto` detection (binary response → logit) are
   exercised by the GWAS demo but not compared against statsmodels
   Logit. The failure modes (perfect separation, single class) are
   covered by the operator's own tests.

3. **Optional method branches are not all covered.** `cluster_axis`
   has three methods (`kmeans`, `hierarchical`, `louvain`); only
   `kmeans` is verified against sklearn. `reduce` has four methods
   (`pca`, `pcoa`, `umap`, `tsne`); only `pca` and `pcoa` are
   verified. The unverified branches are exercised by the pipelines
   they appear in (UMAP in the single-cell pipeline) but the numbers
   they produce are not compared against an external reference.

## Breaking changes from v4

None. The `gene_structure` rewrite changes results for three-level
GFF3 files (gene → mRNA → exon) where the previous implementation
returned zero exons and zero CDS per gene. That is a bug fix, not a
contract change: the input contract, output labels and output shape
are identical. Any pipeline that relied on the previous all-zero
behaviour is itself buggy.

The `interval_overlap` change relaxes an input requirement. Files
that already passed validation continue to behave identically.

## Non-breaking additions

- All v1/v2/v3/v4 task.yaml files continue to run unchanged.
- Existing saved graphs, plugin pins, and installed wheels remain valid.
- Reader contracts are unchanged; no new readers are added.
- No new optional dependencies. `qc_metrics` and `scale_features` use
  NumPy only; the other new operators use existing pandas / scipy /
  statsmodels / lifelines / sklearn.

## Design principles (reaffirmed)

1. **Reader-declared encoding, operator-declared semantics.** Sequence
   operators read the alphabet map from `info`; interval operators
   read column labels from `Form.labels`; neither hard-codes a numeric
   mapping. `interval_overlap` and `peak_nearest_gene` now explicitly
   handle both encoded and unencoded chrom columns via a single
   normalisation rule.

2. **Span over hierarchy.** For annotation QC, span containment is a
   more robust attribution rule than parent-id lookups, because it does
   not assume a particular depth of the GFF3 hierarchy.

3. **External references, not magic numbers.** Every verified operator
   is compared against a published value, an independent
   implementation, or a mathematical invariant. A shape check alone
   is not a verification.

4. **Caller-supplied domain knowledge.** An operator that could
   plausibly need domain knowledge (what is a mitochondrial gene, what
   is a rare allele) takes it as a parameter rather than hard-coding
   it. `qc_metrics` takes a label prefix; `maf` takes a threshold;
   `gc_skew_profile` takes a window size. The operator knows only the
   mathematical structure.

## Honest statement on correctness

The verification suite covers 52 operators across five scripts with
116 checks. Every check compares against an external reference or a
mathematical invariant. Every script also exercises negative cases.

This does not mean the code is bug-free. It means that, for the
specific inputs, parameters and reference implementations used in the
five scripts, the operators produce the correct numbers. The limits
listed in "What is NOT verified" above are the parts where a bug
could still exist without being caught by the suite.

If a downstream user finds a case where an operator disagrees with a
published reference or with an independent implementation, that case
should be added to the relevant verification script before the bug is
fixed, so that the fix is provably correct and does not regress.
