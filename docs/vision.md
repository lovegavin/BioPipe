# BioPipe 的价值主张与设计原则

这份文档是 BioPipe 的产品判断标准。新增算子、Reader、模型、UI 或文档时，先问：它是否让 agent 更低成本地调用**已验证**的工具，而不是让 agent 现写分析代码。

## 1. 核心价值主张

**一个巨大、可维护、经过验证的工具集，让 agent 以最低成本调用分析，而不必自己写代码——从而避免生成实现时的逻辑错误和额外 token 消耗。**

BioPipe 不追求让 agent 生成更多代码；它追求让 agent **少写代码、少猜语义、少返工**。用户给出数据和目标后，agent 应该先查注册表和参考页，在契约边界内组合算子，而不是从零实现统计/IO 逻辑。

## 2. 五个支撑手段

1. **契约化算子库**——注册表 + 两层测试 + 文档索引，agent 在边界内选算子，不靠猜。
   - 注册表给出唯一入口；参考页给出参数、契约、边界；静态检查与运行时校验共同拦截错配。
2. **算子/Reader/ML 模型统一为一等公民**——模型即插件，同一套发现、校验、组合、追溯机制。
   - 不把模型做成特殊分支；模型和普通算子一样声明 schema、contracts、输出和测试。
3. **可视化可追溯**——每步绑定契约与注册表，不只是画布。
   - Studio 中看到的每一步都应能回到算子页面、参数 schema、源码和测试证据。
4. **底层稳定**——合规算子组合行为可预测。
   - 核心层不为单个扩展破例；扩展通过 SDK 和注册表接入；标签、缺失、坐标语义不静默改变。
5. **边际成本趋零**——dsh 批量生成、测试筛真伪，工具集能快速扩大。
   - 生成不是目的，**可验证的生成**才是；没有 oracle、没有边界说明的扩展不进入 stable。

## 3. 差异化一句话

**别人让 agent 现写分析代码，BioPipe 让 agent 调用已验证的工具集。**

## 4. 对设计/评审的直接含义

- 新增能力优先复用既有协议和注册表，不新增旁路。
- 每个 stable 算子必须有可复现的测试证据；能对标权威实现时优先对标，并记录在 `docs/oracle_matrix.md`。
- 文档首先服务 agent 的检索路径：索引 → 候选页 → 必要源码/测试；不要求通读仓库。
- 前端展示应帮助用户理解和微调，而不是隐藏契约。
- 评价扩展的标准是：**可发现、可校验、可组合、可追溯、可维护**，而不是数量本身。
