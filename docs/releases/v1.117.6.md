# Operon 1.117.6

Patch release that finishes the glibc-2.17 install path.

## Findings

Installing `pysam` through micromamba *before* pip put a conda NumPy into the
environment, and pip's resolver then failed with
`ResolutionImpossible ... numpy` when it tried to reconcile the full operator
set (`pydeseq2` wants `numpy>=2`, `cooler` wants `numpy<3`, and several
packages pin older floors). `pysam` has no wheel that runs on glibc 2.17
(manylinux 2.24/2.28 only).

## Change

- The micromamba environment stays minimal (`python=3.11`, `pip`, `bwa`,
  `samtools`), so pip resolves NumPy freely.
- After a successful pip solve the installer calls
  `_ensure_conda_extras()`, which adds `pysam=0.22.1` from
  conda-forge/bioconda with `--strict-channel-priority` when `import pysam`
  fails. Because this happens last, conda cannot perturb the pip plan.
- The pip repair keeps three stages: wheel-only, source-allowed
  (`--prefer-binary`, covers the sdist-only `cooltools`), then compilers plus
  retry.

## Verification

- `pytest tests/test_remote_provision.py tests/test_remote_installation.py
  tests/test_remote_handshake.py`: 49 passed, including a test that `pysam` is
  installed only when missing and that no mamba call happens when it imports.
- Server checks: `pysam 0.22.1` imports on the glibc-2.17 host; a wheel-only
  dry run without `pysam`/`cooltools` resolves.

## Boundaries

`openmm`/`pdbfixer` remain an optional conda-forge extra (see v1.117.3); the
installer prints the command. A pysam source build is not attempted because the
host lacks the htslib build prerequisites.
