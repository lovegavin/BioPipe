# Operon 1.117.10

Patch release for a bootstrapping defect found on the real server.

## Finding

The provision bootstrap started the installer with

```text
<managed>/micromamba-2.10.0 --no-rc run -p <env> <env>/bin/python -I install_linux.py ...
```

Micromamba's `run` subcommand derives the executable name from `MAMBA_EXE` and
requires the file to be called exactly `mamba` or `micromamba`. Because Operon
stores the binary as `micromamba-2.10.0`, the wrapper aborted with
`Error unknown MAMBA_EXE: ... filename must be mamba or micromamba` and a shell
`micromamba-2.10: command not found` line before the installer could start.

## Change

- The bootstrap now exports `PATH=<env>/bin:$PATH` and invokes
  `<env>/bin/python -I install_linux.py ...` directly. The micromamba binary is
  still used for `create`/`install`, where the versioned filename is accepted.
- The provisioning test that asserted the old `run -p` form now asserts the
  direct invocation with `PATH=` set.

## Verification

- `pytest tests/test_remote_provision.py tests/test_remote_installation.py
  tests/test_remote_handshake.py`: 49 passed.
- The manual deployment on the glibc-2.17 host continues to validate the
  dependency plan (pip wheel-only -> source fallback -> conda extras).

## Boundaries

No operator, Reader or schema change.
