# Operon 1.62.0

Third real-inference batch. `esmfold_predict` now loads the full ESMFold 3B
checkpoint from a local directory through `transformers`, and the checksum-
verified weights produced a real prediction for a 118-residue VHH. The library
stays at **653 operators and 101 Readers**.

## Added

- `esmfold_predict` parameter `weights_dir`. When set, the operator loads
  `transformers.EsmForProteinFolding.from_pretrained(weights_dir)` and calls the
  same `infer_pdb` path; when empty it keeps the `fair-esm` behaviour. The
  transformers import is lazy and raises an actionable error if missing.

## Evidence

- Weights: `hf-mirror.com/facebook/esmfold_v1`, `pytorch_model.bin`
  8,442,062,570 bytes, sha256
  `2ee07356b125d1e3e57503c204111fd7323347fc4735d41d3caac57c2a78e116`
  (verified after a clean single-writer download; an earlier concurrent-writer
  attempt inflated the file by exactly 48 MiB and was discarded).
- Real run through `esmfold_predict` (`weights_dir=~/models/esmfold_v1`,
  CPU, `num_recycles=2`, `chunk_size=64`): 118-residue VHH, **879 atoms**,
  `[atom, field]` Form with 12 PDB columns, **mean pLDDT 0.846**, 33.7 s.
- Registry 653/101/7/24 `errors []`; `pytest tests/test_extension245.py`
  passes (fake-loader contract tests); packaging gate passes.

## Boundaries

- ESMFold runs on CPU only here; GPU is untested.
- AntiFold weights remain blocked by an upstream per-connection rate cap
  (~15.6 KB/s), and ColabFold's AF2 parameters by a ~91 KB/s Google Storage
  source; both are documented in `docs/design/hard_capability_status.md` with
  the measured numbers and resumable state.
