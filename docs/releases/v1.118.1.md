# Operon 1.118.1

Patch release from the independent verification of a manual managed install.

## Finding

Inside the managed environment `python -m operon registry check` failed with

```
{"error": {"code": "invalid_request", "message": "Route directory does not exist: .../site-packages/routes"}}
```

because `operon.registry.ROOT` is the package parent (site-packages) once
Operon is pip-installed, while the route YAML files live next to the uploaded
source tree (`managed-v1/code-*/routes`). Passing `--route-root` worked, which
confirmed the operator/reader scan itself was healthy (708 operators,
101 readers, no errors at the time).

## Change

- `operon.registry.default_route_roots()` now resolves route directories for
  both layouts: `OPERON_ROUTES` override, `<root>/routes`, `<sys.prefix>/routes`,
  and `code-*/routes` under the managed root (the `env-*` sibling directories).
  `route_sources()` uses it when no explicit `--route-root` is given.
- New tests `tests/test_registry_layout.py` cover the managed fallback, the
  environment override and `route_sources` discovery.

## Verification

- Source tree: registry check reports **709 operators / 101 Readers / 0 errors**.
- `pytest tests/test_registry_layout.py tests/test_extension348.py`: 7 passed,
  1 skipped.
- Manual server evidence that motivated the fix: `pip check` clean, versions and
  imports healthy, 11 operators only fail on optional external tools
  (OpenMM/pdbfixer, AntiFold, Boltz, Foldseek).

## Boundaries

`openmm`, `pdbfixer`, `antifold`, `boltz` and `foldseek` remain optional
extras; ProteinMPNN-family operators also need the user-supplied weights
(`docs/large_resources.md`). <Operon-directory> is refreshed once for the acceptance
test, then frozen again.
