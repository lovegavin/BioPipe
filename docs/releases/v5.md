# v5 — single-cell, GC skew, peak-to-gene, annotation analysis

## Scope

- Baseline scope of this release: 15 readers, 67 operators, 6 provider
  packages, 6 routes. After the patches below the tree contains 16 readers,
  78 operators, 6 provider packages and 14 routes; the generated registry is
  authoritative.
- The annotation operators (`gff_feature_stats`, `gene_structure`,
  `annotation_gaps`) were introduced for GFF3. This release makes
  them work on GTF as well, and adds the `gtf_annotation` route as
  the first end-to-end pipeline that consumes a GTF.

## Patch: GTF annotation route

### Code

- `src/task/step/steps/_annotation_columns.py`: new private helper.
  Resolves a column by role (`seqid`/`seqname`, `type`/`feature`,
  `attributes`/`attribute`) so the same operator body works on Forms
  produced by `GtfReader` and `Gff3Reader`. Parses GTF `key "value"`
  and GFF3 `key=value` attribute syntaxes in one place.
- `src/task/step/steps/gff_feature_stats.py`: uses the helper.
  Before this patch the operator was documented as GFF3/GTF
  compatible but rejected GTF with
  `StepError: 'type' column is not encoded`.
- `src/task/step/steps/gene_structure.py`: uses the helper and
  attributes exon/CDS records through the annotation's own parent
  chain (GTF `gene_id "X"` directly on the exon/CDS row; GFF3
  `Parent=transcript:Y` on the exon/CDS row, `Parent=gene:X` on the
  transcript row). Span containment is kept only as a fallback for
  attribute-less fixtures.
- `src/task/step/steps/annotation_gaps.py`: uses the helper.

### Route

- `routes/gtf_annotation/task.yaml`: `gff_feature_stats` →
  `gene_structure` → `annotation_gaps`, with histograms.

### Demo

- `tasks/gtf_annotation_demo/`: Ensembl release 110
  S. cerevisiae R64-1-1 GTF and GFF3, downloaded from
  `https://ftp.ensembl.org/pub/release-110`.
- `tasks/gtf_annotation_demo/test_gtf_annotation.py`: standalone,
  not pytest. Includes LF/CRLF consistency, a hand-counted
  two-gene fixture, cross-format equality, and negative cases.

### Verification

- `tasks/verify_gtf_annotation.py`: 18 checks. External references
  are SGD chromosome lengths for R64-1-1 and Ensembl release 110
  feature counts. Cross-format comparison uses the same Ensembl
  release dumped twice; CDS totals are compared modulo the Ensembl
  stop-codon convention.
- Existing demos and pytest fixtures pass.

  `gene_id=X`, and GFF3 `ID=gene:X` are all recognised.
- `_normalise_chrom` now unifies the common mitochondrial
  aliases `Mito`, `MT`, `chrM` to `chrM`.

### Demo

- `tasks/peak_nearest_gene_demo/test_peak_nearest_gene_gtf.py`:
  standalone test. Runs the operator on a GTF input, verifies
  auto-resolution (`b_chrom=seqname b_type=feature

### Verification

- Existing `test_peak_nearest_gene.py` still passes (11 checks).
- New GTF test passes (2 checks).

`peak_nearest_gene` input contract no longer references any

## Patch 3: BGEN dosage QC route

### Reader changes

- `src/reader/readers/bgen_reader.py`:
  - The reader silently accepted files it could not represent
    correctly. Two cases now raise `ReaderError` with an
    explicit message before producing a wrong Form:
    - Non-biallelic-diploid data: `bgen_reader` returns more
      than 3 genotype columns per variant, or the three
      genotype probabilities do not sum to 1.0. This covers
      haploid and haplotype BGENs such as
      `tasks/bgen_demo/input/haplotypes.bgen`, which has 4
      genotype columns.
    - Complex BGENs (per-variant allele-count or ploidy
      variation). `bgen_reader` requires `allow_complex=True`;
      the reader now converts the resulting `ValueError` into a
      clear `ReaderError` naming the unsupported feature.
  - No behaviour change for biallelic diploid BGENs.

### Route

- `routes/bgen_qc/task.yaml`: `missing` (sample) →
  `missing` (variant) → `maf` → `ld_prune` → `pca` →
  `scatter` + `describe`. Runs on a real BGEN file.

### Why HWE is not in this route

`hwe` requires `representation == "hard_call"` and `ploidy == 2`.
This is a mathematical constraint, not a bug: the Wigginton
exact test takes integer genotype counts (n_hom_ref, n_het,
n_hom_alt). A continuous dosage vector is not compatible with
that test. The route therefore stops at `ld_prune` and `pca`,
which are representation-agnostic.

### Demo

- `tasks/bgen_qc_demo/`: `example.bgen` from the bgen-reader
  test suite (199 variants × 500 samples, biallelic diploid).
- `tasks/bgen_qc_demo/test_bgen_qc.py`: standalone test.
  Verifies the reader's dosage range, independent-recomputation
  agreement for `maf` and `missing`, an `ld_prune` invariant,
  and a PCA component-variance invariant. Also verifies that
  both non-diploid BGEN files raise `ReaderError`.

### Verification

- `tasks/verify_bgen_qc.py`: 14 checks. External reference is
  an independent NumPy implementation of dosage, MAF, and
  missing rate on the same matrix, plus mathematical
  invariants for PCA. Two negative cases confirm the reader's
  rejection paths.

### Honest statement on correctness

Verified: reader output shape, representation, ploidy, dosage
range, MAF and missing-rate agreement with independent
recomputation, PCA component variance ordering, both rejection
paths.

Not verified: no public real-world BGEN with a published
reference MAF or PCA is included in this repository. UK
Biobank BGEN requires authorization; 1000 Genomes publishes VCF
rather than BGEN. The reader itself is the target of this
verification; the operators tested against it are independent
of the file format.

Out of scope for this reader: multi-allelic, haploid, or
complex BGEN files. Those must be converted to VCF first.

### Input boundary document

- `docs/input_boundary.md`: the full list of supported starting
  files, the explicit out-of-scope list (FASTQ, BAM, mzML, CZI,
  etc.), and the four admission criteria for a new Reader. The
  `BgenReader` change in this patch is the first application of
  those criteria; the reader was narrowed rather than expanded.

## Patch 4: single-cell QC + clustering route

### Route

- `routes/single_cell/task.yaml`: `qc_metrics` →
  `filter_by` (cells) → `filter_min` (genes) →
  `normalize(total)` → `log_transform(ln)` →
  `rank_axis` (top 2000 variable genes) →
  `reduce(pca, 50)` → `reduce(umap, 2)` →
  `cluster_axis(louvain)` → `compare_groups(one_vs_rest,
  wilcoxon)` → `scatter` + `describe`.

### Why total normalize and ln, not cpm and log2

The route was tried first with `normalize(cpm, target_sum=1e6)`
and `log_transform(base=2)`. On this PBMC 3k filtered matrix
that chain produced a PCA whose first two components captured
41% of total variance, and Louvain returned a single community.
Switching to `normalize(total)` plus `log_transform(base="e")`
gave a PCA with 4% variance in the first two components and 15
Louvain communities, matching `tasks/scrnaseq_demo` on the same
data. Both chains are mathematically valid; the chosen one
exposes cluster structure on this dataset.

`normalize(total)` divides each cell by its own total so every
cell sums to 1. `target_sum` only applies to `cpm`; the route
does not pass it.

### Demo

- `tasks/single_cell_route_demo/`: 10x Genomics PBMC 3k
  filtered matrix (32738 genes × 2700 cells), downloaded from
  `https://cf.10xgenomics.com/samples/cell/pbmc3k/pbmc3k_filtered_gene_bc_matrices.tar.gz`.
- `tasks/single_cell_route_demo/download.sh`: idempotent
  download and extract.
- `tasks/single_cell_route_demo/test_single_cell_route.py`:
  standalone. Hand-counted `qc_metrics` and `filter_by` on a 4×4
  fixture; total-normalize sum invariant; ln exactness against
  NumPy; HVG top-2000; PCA 50 components with decreasing
  variance; Louvain ≥ 2 clusters; wrong `feature_dim` rejected.

### Verification

- `tasks/verify_single_cell.py`: 15 checks. External reference
  is independent NumPy recomputation of per-cell total,
  n_detected, and log transform, plus the published 10x
  Genomics PBMC 3k summary (median 2197 UMIs and 819 genes per
  cell). Mathematical invariants cover total normalize
  (per-cell sum == 1), ln exactness, HVG ordering, PCA component
  variance ordering, and Louvain cluster count.

### Honest statement on correctness

Verified: reader shape, per-cell QC against independent NumPy,
two 10x-published median values, total-normalize and ln
invariants, HVG top-2000 selection, PCA 50 components with
monotonic variance, Louvain ≥ 2 communities (15 in this run).

Not verified: cluster biological identity (no cell-type
annotation in this route), UMAP projection values (visual only),
marker gene identity (Wilcoxon statistics are checked for
shape and finiteness, not for published marker associations).

### cluster_axis output convention

`cluster_axis` writes one cluster id per position into
`form.data`, and declares a single dummy label on the `cluster`
axis. Downstream consumers read `form.data[:, 0]` as the cluster
assignment. The single-cell test and verification scripts use
`len(set(clusters.data[:, 0]))` to count communities; reading
`clusters.labels["cluster"]` returns 1 by design.

## Patch 5: GO enrichment route + gene_list_to_hits operator

### New operator

- `src/task/step/steps/gene_list_to_hits.py`: takes a
  `gene × go_term` universe matrix and a list of gene labels,
  returns a new matrix containing only the rows whose gene is in
  the list, with values `universe > 0`. The output is a valid
  hits Form for `enrich_go`: gene axis is a subset of the
  universe, term axis matches exactly.

  A previous draft kept the full universe shape and zeroed
  non-hit rows. `enrich_go` uses the hits form's row count as
  `n` (number of hit genes), so that shape gave `n = N`, and
  every p-value collapsed to 1. The operator now drops non-hit
  rows instead.

  Parameters: `genes` (list of labels, required), `gene_dim`,
  `term_dim`, `output`. Gene labels must exist on the universe;
  unknown labels raise `StepError`.

### Route

- `routes/go_enrichment/task.yaml`: GAF → `pivot` (gene ×
  GO term universe) → `gene_list_to_hits` (p53 pathway member
  list) → `enrich_go` (hypergeometric, FDR) →
  `enrichment_plot` → `describe`.

### Demo

- `tasks/go_enrichment_route_demo/`: `goa_human.gaf.gz`
  (GO Consortium human annotations, 881380 rows) plus the p53
  member gene list. Route runs in under 10 seconds.

### Verification

- `tasks/go_enrichment_route_demo/test_gene_list_to_hits.py`:
  5 checks. Hand-counted hits matrix, missing-gene rejection,
  hand-counted hypergeometric p-value (1/6), full GAF chain.
- `tasks/verify_go_enrichment.py`: 10 checks. Independent
  `scipy.stats.hypergeom.sf` comparison on synthetic data
  (p-values match exactly), plus real GAF chain invariants:
  all p in [0,1], all q in [0,1], at least one q < 0.05 (59
  terms), and the Benjamini-Hochberg monotonicity property
  p ≤ q for every term.

### Honest statement on correctness

Verified: `gene_list_to_hits` row subset and 0/1 values,
`enrich_go` p-values against scipy.hypergeom.sf, BH property
on real data, and the complete GAF → hits → enrichment chain.

Not verified: biological interpretation of the 59 significant
terms. The p53 member list is fixed input to demonstrate the
route, not a discovery claim. The GAF snapshot is from a fixed
GO Consortium release; term counts drift between releases.

  ORF on ATGGCTTAA; SARS-CoV-2 length (29903) and GC (0.3797)

- `tasks/verify_sequence_features.py`: 11 checks. Per-sequence

  against Python `str.count`.

### Notes

`sequence_stats` reports GC as `(C + G) / length` with the raw
sequence length as denominator, not the non-N length.
`valid_ratio` is 1.0 for any sequence using only characters
present in `alphabet_map`; N is mapped and therefore counts as
valid. Both conventions are asserted explicitly in the demo
test.

`find_orfs` reports `length_aa` excluding the stop codon.
For ATGGCTTAA the three codons are ATG, GCT, TAA; the reported
`length_aa` is 2.

## Patch 7: multi-omics integration route + TenxH5Reader

### New reader

- `src/reader/readers/tenx_h5_reader.py`: reads 10x Genomics
  Cell Ranger `filtered_feature_bc_matrix.h5` files.
  - `feature_type` parameter selects a subset of features:
    `"Gene Expression"` reads genes, `"Antibody Capture"` reads
    surface antibodies. Omitting it returns every feature.
  - `feature_id_field` selects the feature label source: `"name"`
    (gene symbol / antibody name) or `"id"`.
  - `info["feature_types"]` and `info["genome"]` are declared
    axis-parallel on the feature axis.
  - Uses `reader_contract(extra=...)` instead of
    `reader_contract(representation=...)`: the latter forces a
    `ploidy` field on the output Form, which is wrong for a

## Patch 9: per-model ML operators (classification + regression)

### Design change

`train_classifier` from patch 8 was a single operator with a
`method` parameter selecting one of four algorithms. That mixed
task kind (classification) and algorithm choice (logistic / rf /
svm / gb) into one parameter and forced a schema union of four
models. It is replaced by one operator per model, in
classification and regression versions.

Files starting with `_` are not registered; `_ml_common.py` holds
the shared logic.

### Shared logic

- `src/task/step/steps/_ml_common.py`:
  - Sample alignment, missing-fill, train/test split, K-fold CV.
  - Classification: macro precision / recall / F1, AUC,
    confusion matrix, `StratifiedKFold`.
  - Regression: RMSE, MAE, R2, `KFold`.
  - Feature importance from `coef_` (linear) or
    `feature_importances_` (trees).
  - Classification-only parameters: `valid_labels`, `C` on the
    linear models, `class_weight`, `n_estimators` and
    `max_depth` on the tree models.
  - Regression target may be encoder-wrapped (for example a
    numeric column in a clinical table that also carries a
    `data_type` declaration row). The operator recovers numeric
    values from `encoder.inverse` and treats unparseable
    entries as missing. If no numeric value survives, the
    operator raises `StepError`.

### Operators

Classification (4):
- `logistic_regression` — `C`, `penalty`, `class_weight`
- `random_forest_classifier` — `n_estimators`, `max_depth`,
  `class_weight`
- `svm_classifier` — linear kernel, `C`, `class_weight`
- `gradient_boosting_classifier` — `n_estimators`,
  `learning_rate`, `max_depth`

Regression (6):
- `linear_regression` — OLS
- `ridge_regression` — `alpha`
- `lasso_regression` — `alpha`
- `random_forest_regressor` — `n_estimators`, `max_depth`
- `svm_regressor` — linear epsilon-SVR, `C`, `epsilon`
- `gradient_boosting_regressor` — `n_estimators`,
  `learning_rate`, `max_depth`

Every operator outputs `[feature_dim, "statistic"]` with
`importance` and `signed_score` columns. Regression targets must
be numeric; passing an encoded categorical column raises
`StepError`.

### Removed

- `src/task/step/steps/train_classifier.py` and its demo test,
  verification script and route references are gone.

### Routes

- `routes/ml_classification`: three classifiers run side by side
  on the same CPTAC proteomics matrix (`Stage` target,
  `valid_labels=[Stage I, Stage II, Stage III]`, `C=100` for
  linear models).
- `routes/ml_regression`: three regressors run side by side on
  the same matrix (`Age` target, 30–90, no missing).

### Verification

- `tasks/ml_classification_route_demo/test_ml_classification.py`:
  6 standalone checks. Perfect-separation sign check on logistic
  and SVM, RF importance non-negative, GB importance sums to
  positive, single-class rejection, three-classifier CPTAC
  end-to-end run.
- `tasks/ml_regression_route_demo/test_ml_regression.py`: 6
  standalone checks. Exact OLS recovery on a `y = 3*x0 - 2*x1`
  dataset (`scale=False`), ridge shrinkage, lasso sparsity
  (19/20 zeros on one-signal data), RF / SVR / GBR run, encoded
  categorical target rejected, three-regressor CPTAC Age
  end-to-end run.
- `tasks/verify_ml_classification.py`: 27 checks. Signal
  recovery in a 20-feature synthetic dataset for four
  classifiers (F0 in top 3 by importance for every model; top 3
  rather than top 1 because linear SVM is non-unique and tree

### Honest statement on correctness

Verified: coefficient signs and magnitudes against
hand-computable cases, closed-form OLS reference for linear
regression, sparsity behaviour of lasso, importance ordering
for four classifiers on a signal-plus-noise synthetic
dataset, exact rejection of categorical regression targets,

Not verified: published CPTAC classifier accuracy or age

The `svm_classifier` still emits a scikit-learn `FutureWarning`

### Deep learning scope

Still no deep-learning operator. The ten operators in this
patch are all scikit-learn. Deep-learning operators, when
added, will be built on PyTorch only.
