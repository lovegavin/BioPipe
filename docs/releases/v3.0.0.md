# Operon Studio 3.0.0

Operon Studio is now **Operon Studio**. Compatibility Python modules, CLI aliases,
MCP tool identifiers and serialized format identifiers retain their existing names.
The release uses one Windows Setup with an isolated, lightweight management Python;
scientific dependencies are prepared explicitly for selected workflows.

## Workflow authoring and collaboration

- Strict public YAML with separate frozen parameter and execution JSON files;
  offline lint/format, graph import/export and direct terminal execution.
- Import Python/R/C/C++ scripts as workflow nodes with file contracts. Python
  literal candidates can become independently saved parameters. Promote a script
  into a normal library provider without changing the execution engine.
- SDK 3.6 representation contracts and explicit, visible format adaptation;
  incompatible semantic structures still require a deliberate analysis operator.
- Inspect coherent agent changes on the canvas and undo a batch as one edit.
  Existing selection context, revision checks and separate run permissions remain.
- Script dropping and new-canvas handling include the RC4 fixes. Unchanged library
  refresh avoids rebuilding unchanged provider packages.

## Server and terminal operation

- `operon environment status/check/prepare` exposes the actual service runtime,
  selected-route readiness and explicit dependency preparation without a window.
- `--workspace .` uses the current shell directory. Malformed YAML is rejected
  before a persistent service is started. Blocked readiness returns exit code 1.
- `run --progress` reports status changes on stderr while stdout remains JSON.
- Script failures retain full native logs and include a bounded diagnostic tail
  in the main task log. Invalid memory settings return structured validation errors.
- New clients require `workflow_readiness` during SSH handshake, so an older
  server is rejected before a run rather than failing midway through validation.
- The same memory planner, host admission, spill, streaming, task history and
  independent parameter snapshots are used on Windows and Linux.
- Container startup headroom accounts for clean inactive file cache while retaining
  parent limits, dirty-page exclusions, the frozen snapshot and emergency spill.
- Windows dependency probes and their logs support deep profile directories.
  Corrupt workflow archives return an actionable validation error without stopping
  the service. Explicit dependency preparation remains cancellable during shutdown.
- Official v2.6.0 routes can resolve their bundled implementations in a fresh
  profile using verified release receipts. Frozen parameter values remain intact;
  third-party wheel identities and package/operator version boundaries stay strict.

## Installation and release boundaries

`Operon_Setup.exe` is the end-user Windows download. Application wheels/source are
for server and developer installations. The reference library is independently
versioned and can be updated separately; this application release includes the
tested 2026.11.6.1 seed, not every later author library release.

Each installation/reinstallation has its own program directory, interpreter and
profile. Existing Operon profiles and global interpreter preferences are retained.
Routine server reconnects continue to reuse the server installation document.
Upgrade a 2.6 server explicitly before using the new selected-host readiness RPC.

The new CLI is not a Nextflow executor. Submission IDs reuse complete task receipts;
they do not provide per-node checkpoint resume. Automatic private environments for
inline scripts, Slurm/container executors and arbitrary native standalone exports
remain future milestones. Optional scientific operators and tools require their
own compatibility and numerical acceptance.

Windows interactive acceptance and real Linux terminal evidence are tracked
separately. Unit tests and package probes alone do not constitute double-click
installation or a clean-machine scientific-library acceptance.
