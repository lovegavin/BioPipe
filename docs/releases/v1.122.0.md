# Operon 1.122.0

## Multi-environment execution

Operators whose runtime cannot coexist with the shared stack now execute in a
dedicated interpreter instead of failing or downgrading NumPy/Torch:

- `operon/environments.py` gains `run_step()` and `proxy_step()`: inputs and
  outputs travel through a temporary directory (NumPy arrays plus JSON metadata,
  label encoders serialized as mappings), and the worker imports only the step
  module under the environment interpreter.
- `operon/env_worker.py` reconstructs the Form inputs, runs the step with a
  minimal context, and returns the output Form and export payload as JSON.
- `src/task/step/__init__.py` returns the proxy for any descriptor whose
  `resources.environment` is set, so the runner, services and MCP never import
  the conflicting module in the host interpreter.
- All six `esm3_*` operators declare `resources.environment = "esm3"`, and
  `operon/environments.json` records the ESM-3 recipe (Python 3.12,
  torch >= 2.11 + triton 3.6, ESM from GitHub). Weight downloads use
  `HF_ENDPOINT=https://hf-mirror.com` by default inside the bridge.

## Verification

- `tests/test_environments.py` exercises the bridge end to end
  (`structure_interface_core` through a fake interpreter) and the missing
  environment error path.
