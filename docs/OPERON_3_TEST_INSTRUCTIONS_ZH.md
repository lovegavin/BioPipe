# 可转发给测试机的 Operon 3.0.0 验收指令

**本次是 RC8 候选包，请解压完整测试 ZIP，勿用 RC7 或更早的安装包替代。**
先确认根目录有 `FORWARD_TO_TESTER.txt`、`SHA256SUMS.txt` 和安装 EXE。
若通过 KMFU 对拷线传包，完成粘贴和 SHA256 校验后先关闭测试机的 KMFU，
确认全屏隐形窗口不再遮挡，然后才开始电脑操控验收。
RC4 的脚本拖入修复已有单独验收；本次补齐 CLI 与服务器入口，并修正 Linux
容器干净文件缓存导致预算过低的问题，以及 Windows 深路径依赖检查、损坏路线
压缩包的错误提示。RC8 还补齐官方 2.6.0 算子的发布兼容记录：使用原验收
导出的旧 ZIP，在全新档案中导入、验证、运行，确认输入连线与冻结参数保留，
不需要手动 repin。记录更新证据，但不要修改旧文件。Windows 界面保持 RC4
修复，回归下面三项。
使用新的隔离档案，不能拿旧版已刷新过的档案代替首次刷新：
①新建未保存画布，从资源管理器把至少 6 个脚本拖入，Ctrl+A 后删除全部，
再拖入。重复至少 5 轮；分别落在中央提示图案、添加输入按钮、普通网格处，
并覆盖保存前后、切换标签页、关闭重开画布和快捷方式重开。记录每次耗时和
成功次数；每个脚本仅产生一个节点，错误脚本不能留下半成品。必须实际 OS 拖入，
不能用 API 或模拟浏览器事件替代这一项。
②启动后立即新建画布，连续新建/切换标签页；画布和选区最终应能被 Agent 读到，
不得出现 `Presence references an unknown document`，也不能丢草稿或停掉同步。
③记录全新档案首次刷新、无修改再次刷新的耗时。无修改时不应重装/预编译全部
内置库，任务数不变。再用唯一 ID 添加合成算子并刷新，确认真实变更仍能生效；
编辑和脚本检查在刷新期间保持响应。本机计时仅供比较，不代表测试机耗时。
此外，回归“保存新算子立即可见”，无须手动刷新，清空搜索和重开后仍可见。
RC3 尚未验证的旧路线导入、原图实际打开、节点拖动、多选复制撤销和 SDK 3.6
转换界面/实际运行继续列为待验收，不得自动写成通过。若旧路线样本缺失，请明确
记录缺失，不要伪造一个当前版本导出包来宣称旧版本兼容。
启动提示改为“正在启动工作台服务”，仍会启动轻量 Python 管理进程，
不能据此宣称已经实现完全不启动 Python 的桌面。

包内 manifest 应为 `runtime_mode: management`。保留 NumPy 作为 Form／内存／
预览基础，但不预装 Pandas、SciPy、Matplotlib、PyTorch 等分析库。
首次 Validate 提示缺分析依赖是预期行为；仅在显式“安装当前路线所需依赖”后
联网准备，然后再次验证和运行。不能在启动或刷新算子库时偷偷安装。
Agent 的 backend 阶段额外传 `--prepare-environment`，明确授权仅准备合成路线。
下面独立诊断命令传 `--prepare-analysis`，同时验证实际 PCA 和 PNG/PDF/SVG；
它仍不替代界面测试。检查依赖安装进新档案的管理目录，应用 runtime 仍无这些
分析库，旧 Operon 档案和全局 runtime.json 仍不变。

请验收本次收到的 **Operon_Setup.exe 3.0.0 候选包**，先核对随包 SHA256
清单。请阅读同包 `OPERON_3_TEST_ACCEPTANCE.md`；详细步骤以该英文指南为准。
这是实际安装验收，不发布，不修改或清理旧 Operon、旧档案、旧证据、系统
Python、Conda 或 VS Code。使用新的独立测试目录保存报告和证据。

可选先补一项“安装包后端诊断”：使用**本次安装的随包 Python**运行以下
命令。report 文件和 work-dir 都必须是新的，work-dir 尚不存在，证据路径
必须在安装目录之外；不要加 `--allow-development`。

```powershell
& '<安装代码目录>/runtime/python/python.exe' -I `
  '<安装代码目录>/scripts/verify_operon_candidate.py' `
  --version 3.0.0 --prepare-analysis `
  --report '<新证据目录>/candidate.json' `
  --work-dir '<新证据目录>/candidate-work'
```

该脚本在新 work-dir 内使用临时用户目录和独立合成档案，不修改实际桌面
档案或安装身份。它测试安装包 API、参数提取/冻结、YAML、真实分支 worker、
内存记录和后端正常退出；其样例是四行数据、×5/×7，和下面手工样例不同。
它**不替代**实际双击安装、快捷方式启动、界面操作及 Agent 六阶段，报告中
必须分开列出。失败时保留 report 和整个 work-dir。

1. **实际双击安装。** 在资源管理器双击 Setup，记录耗时、安装目录、安装
   日志。通过安装器或新桌面快捷方式打开实际 Operon Studio，确认窗口显示
   Operon、版本 3.0.0、图标正常。不得用命令行启动后端代替此项。
2. **新环境与旧版隔离。** 从本次安装凭据和启动日志确认随包 Python、安装
   ID、新档案和工作区；新安装应使用 `.operon/profiles` 下的新档案。记录
   旧 Operon 的全局 runtime.json、旧快捷方式/卸载登记、已约定的旧档案及
   provider wheel 样本基线。新安装不得改写旧全局解释器记录、自动迁移旧
   注册表或删除旧数据。
3. **启动不偷偷装科学依赖。** 空闲启动和读取算子库期间查看任务数、子进程
   和依赖日志：不能自行启动分析任务、pip/conda/R 包安装。管理后端启动和
   随包环境完整性检查正常；不要为了通过测试关闭依赖检查开关。
4. **Agent 六阶段。** 用本次安装目录里的 `scripts/verify_release_agent.py`，
   显式传 `--version 3.0.0`、实际 Python/代码目录/工作区/桌面 instance ID。
   依次完成 backend、open、capture、apply、undo，重开后完成 retry。
   capture 前必须在 EXE 中真实单击 PCA；观察批量修改、活动记录的前后差异
   和单次撤销。编辑不能自行增加运行任务。重开使用新 instance ID、同一
   evidence 目录，必须复用原任务。不要使用 `--allow-headless` 或伪造选区。
5. **旧路线和节点操作。** 在新档案中导入之前验收保存的合成 v3/v3.5 路线，
   检查连线、参数和内存设置；不要改原文件。检查节点本体拖动、Ctrl+单击
   多选、两节点 Ctrl+C/V、内部连线和撤销。剪贴板权限提示不等于粘贴成功。
   从结果页实际打开原始 PNG、PDF、SVG。
6. **临时脚本与冻结参数。** 使用随包 `script_pipeline` 示例：把 generate.py
   和 scale.py 拖入画布，接线并复制为两个缩放分支。原始 factor 默认均为 2。
   在代码界面“保存代码并检查”，勾选 factor 并“提取到参数 JSON”；确认
   默认值确实是 2。把 A 分支设为 3、B 分支设为 2，保存、验证后主动运行。
   输入是 1、2、3、4、5，输出应分别为 3、6、9、12、15 和 2、4、6、8、10。
   重开保存路线后值保持；只在导出副本中改 schema default，不改显式值，
   再导入时也不能覆盖已冻结的 3。选择类别、用唯一 ID 保存为普通算子，
   确认立即出现在该类别并有 JSON/Markdown；这一步不能自行装依赖或运行。
7. **YAML 与类型错误。** 从文件菜单导出“可编辑 YAML 项目”，再导入，核对
   分支、参数、执行设置和连线。用随包解释器运行 lint/format --check。
   复制 scale.py，仅把输入声明改成 file.tsv，连接 CSV 输出后应阻止运行，
   不能擅自解释成其他格式。按英文指南运行安装版本的 matrix→list 拒绝诊断。
   如果没有 SDK 3.6 转换节点 UI 样例，转换标识的界面实测应写“未测”，不能
   用组件诊断冒充实际界面或内存运行验收。
8. **Readiness 负例。** 在一次性脚本副本声明 `numpy==0.0.0`，只执行 Validate，
   确认明确报依赖不匹配、无 pip 自动安装、无新增任务；不要安装这个故意错误
   的版本。删除负例，恢复标准库脚本，验证通过后再主动运行。脚本冲突依赖
   的自动私有目录准备仍是边界，不把此项记为已支持。
9. **设置、重开、重装、卸载。** 英文/深色/默认查看器设置应在重开后保持，
   切换设置栏目不能丢服务器表单草稿。记录首次、快捷方式重开和重装启动后
   正常关闭的耗时、后端退出码和残留进程。再次实际双击同一 Setup，应创建
   新软件目录和新空档案，前一测试档案/结果哈希不变。仅用 Windows 卸载
   本轮 Operon，保留测试档案与证据，复核旧版基线，列出保留缓存/未知文件。
10. **CLI 回归。** 用本次随包 Python 的 `-m operon --version` 确认 3.0.0；
    `help server` 应返回服务器指引。通过实际桌面工作区查询 `environment status`，
    核对解释器、工作区及显式依赖准备策略。直接对导出的 YAML 执行
    `environment check`，随后用 `run --progress --brief` 主动运行标准库脚本路线；
    确认进度写 stderr、最终 JSON 写 stdout、任务在运行记录中可见。
    无效 YAML 应返回非零和可读错误，不能新增任务。
    导入一个内容损坏的 ZIP 副本，应明确提示“Invalid workflow archive”，
    不返回服务器内部错误，随后仍能正常导入有效路线或新建画布。
    Setup 的隔离档案禁止越权覆盖工作区；不要为了使用独立目录绕过安装身份。
    `scripts/verify_server_cli.py --prepare-analysis` 是源码/独立 wheel 环境的终端验收，
    本轮已另在 Windows 和真实 Linux 运行，不能拿它冒充桌面 UI 操作。

每项分别标明 **通过 / 失败 / 未测**。失败请给确切操作、报错、相关堆栈和
截图；没有执行的操作不要写成通过。回传验收报告、仅本轮日志/截图/Agent
报告/合成路线的证据包及 SHA256，不包含令牌、凭据或用户数据。结尾注明
**未发布**。这次 Windows 合成验收不代表 Linux、Hi-C 科学结果、全部算子或
任意 R/C/C++ 工具链、通用独立导出都已通过。
